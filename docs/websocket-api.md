# WebSocket API Guide

This document describes the WebSocket API for the Benchmarking Platform. The API is designed for real-time interaction, allowing clients to perform actions, receive updates, and monitor benchmark progress.

## 🔗 Connection

- **Endpoint**: `/ws`
- **Authentication**: Authentication can be handled via a `token` query parameter or a `token` cookie.
- **Workspace Context**: An optional `workspace_id` query parameter sets the initial workspace context.

**Example URL:**
```
ws://localhost:8080/ws?token=YOUR_JWT_TOKEN&workspace_id=YOUR_WORKSPACE_UUID
```

---

## 📦 Message Protocol (Envelope)

All messages exchanged via WebSocket (both sent by the client and received from the server) follow a standard JSON **Envelope** structure.

| Field | Type | Description |
|---|---|---|
| `type` | `string` | The message type identifier (e.g., `REQ_GET_ME`, `EVT_RUN_FINISHED`). |
| `correlation_id` | `string` | A unique ID generated by the client to match requests with their asynchronous responses. |
| `payload` | `object` | The actual data structure for the specific message type. |

### Message Type Prefixes
- **`REQ_`**: Requests sent by the client that expect a corresponding `DATA_` response.
- **`CMD_`**: Action commands sent by the client (may trigger events or state changes).
- **`DATA_`**: Responses containing requested data, matching a request's `correlation_id`.
- **`EVT_`**: Unsolicited events sent by the server to notify clients of changes.

## 🛠 Handshake & Authentication

### 1. Request Current User Profile
**Type**: `REQ_GET_ME`  
**Payload**: `{}`  
**Response**: `DATA_ME`

**Response Payload Example:**
```json
{
  "user": {
    "id": "uuid",
    "name": "User Name",
    "email": "user@example.com",
    "is_admin": false,
    "workspaces": [...],
    "organizations": [...]
  },
  "organization": {
    "id": "uuid",
    "name": "Org Name"
  }
}
```

### 2. WebSocket Login
If not already authenticated via cookie/query param.  
**Type**: `REQ_WS_LOGIN`  
**Payload**:
```json
{
  "email": "user@example.com",
  "password": "password",
  "organization_id": "optional-uuid"
}
```
**Response**: `DATA_WS_LOGIN_RESULT`

## 📂 Workspace Management

### List Workspaces
**Type**: `REQ_GET_WORKSPACES`  
**Payload**: `{}`  
**Response**: `DATA_WORKSPACES` (Array of workspace objects with `agent_count`)

### Switch Workspace
Updates the socket's context and provides a new JWT token scoped to the selected workspace.  
**Type**: `REQ_SWITCH_WORKSPACE`  
**Payload**: `{ "workspace_id": "uuid" }`  
**Response**: `DATA_RESPONSE` containing `{ "token": "...", "workspace": {...} }`

### Clone Workspace
**Type**: `REQ_CLONE_WORKSPACE`  
**Payload**: `{ "source_workspace_id": "uuid", "new_name": "New Name" }`  
**Response**: `DATA_RESPONSE` with the new workspace object.

## 🚀 Benchmark Runs (Commands & Events)

### Start a Run
**Type**: `CMD_START_RUN`  
**Payload**:
```json
{
  "question_set_id": "uuid",
  "agent_ids": ["uuid1", "uuid2"] // Optional, defaults to all enabled agents
}
```

### Real-time Monitoring Flow
When a run starts, the server emits several events to all connections in the workspace:

1. **`EVT_TASK_STARTED`**: A specific agent began processing a question.
    - Payload: `{ "run_id": "...", "agent_id": "...", "question_id": "..." }`
2. **`EVT_TASK_COMPLETED`**: An agent finished a question.
    - Payload: `{ "run_id": "...", "agent_id": "...", "question_id": "...", "success": true, "answer": "...", "duration_ms": 1234 }`
3. **`EVT_RUN_FINISHED`**: All tasks in the run are complete.
    - Payload: `{ "run_id": "...", "status": "completed", "total_tasks": 10, "completed": 10 }`

## ⚡ Data Syncing & Lazy Loading

For performance, large objects like benchmark results are often handled via lazy loading.

### Full State Sync
**Type**: `REQ_SYNC_STATE`  
Fetches agents, question sets, and recent runs for the current workspace.  
**Response**: `DATA_STATE`

### Lightweight Run Data (Lazy Load)
**Type**: `REQ_GET_RUN_LITE`  
Returns run metadata and a list of result headers (IDs and content hashes) WITHOUT the large `answer` text.  
**Response**: `DATA_RUN_LITE`

### Get Specific Result Details
**Type**: `REQ_GET_RESULT_DETAILS`  
Fetches the full `answer` and metadata for a list of result IDs.  
**Payload**: `{ "result_ids": ["uuid1", "uuid2"] }`  
**Response**: `DATA_RESULT_DETAILS`

## 💻 Frontend Implementation (Vue/JS)

In the frontend, we use a `wsService` to manage correlations and promises.

### Sending a Request
```javascript
// Example from src/services/websocket.js
async request(type, payload) {
    const correlationId = uuidv4();
    const message = {
        type,
        correlation_id: correlationId,
        payload: payload
    };

    return new Promise((resolve, reject) => {
        // 1. Register listener for the specific correlationId
        this.handlers.set(correlationId, (response) => {
            if (response.type === 'EVT_ERROR') {
                reject(response.payload);
            } else {
                resolve(response.payload);
            }
        });

        // 2. Send the message
        this.socket.send(JSON.stringify(message));

        // 3. Optional: Set timeout
        setTimeout(() => {
            if (this.handlers.has(correlationId)) {
                this.handlers.delete(correlationId);
                reject(new Error(`Timeout for request: ${type}`));
            }
        }, 30000);
    });
}
```

### Listening for Events
```javascript
// Subscribe to global events (like task updates)
wsService.on('EVT_TASK_COMPLETED', (payload) => {
    console.log('Task finished:', payload.answer);
    // Update state in Vue/Pinia
});
```

## ⚠️ Error Handling

Errors are returned as envelopes of type **`EVT_ERROR`**.

```json
{
  "type": "EVT_ERROR",
  "correlation_id": "original-id-if-available",
  "payload": {
    "error": "Short error message",
    "details": "Technical details (only in development)"
  }
}
```
